# Forms and Documents

Purchase Orders are the first TenOps Form. Future Letters of Transmittal, Quote Requests, vendor forms, and shop documents must reuse the same separation of concerns:

1. Structured business record or current editor state.
2. A document-specific print model.
3. One canonical document renderer.
4. The shared `DocumentViewer` presentation shell.

`DocumentViewer` owns preview chrome, loading and error states, filename and metadata, zoom, open/download/print actions, attachment sequencing, responsive overlay behavior, and unsupported-file fallback. It does not own Purchase Order layout or calculations.

Draft preview remains a browser renderer for current editor state. Permanent Purchase Order PDFs are first-class business documents with their own deterministic renderer. That renderer accepts only the immutable issuance header and line snapshots through a document-specific model; it never prints the React UI or queries current Vendor, Job, Catalog, or draft records.

Permanent artifacts are generated by a Supabase Edge Function and stored once in the private `purchase-order-documents` bucket. Generation is independent from issuance, retryable after failure, and one-to-one with an issuance. Download returns the stored artifact through a short-lived signed URL and never regenerates it.

Production attachments use signed storage URLs and the same viewer for PDF, PNG, JPEG, and WebP. Unsupported types retain open/download access without unreliable conversion.

Future Forms and Production launch points must open the shared `PurchaseOrderEditor`; there is no separate job-specific PO implementation. Save Draft never generates an artifact. Successful issuance initiates a best-effort permanent-PDF request, while explicit status, retry, and original-download actions remain available on the issued record. Pending Receivals, revisions, and vendor delivery remain separate post-issuance extensions.

## Letters of Transmittal

Letters of Transmittal are job-scoped Production documents. The Production
Inspector opens a focused composer and newest-first history for the selected
canonical `jobs.id`; there is no global Transmittal workspace.

An unsaved preview sends the current browser payload to the dedicated
`generate-job-transmittal-pdf` Edge Function. It creates no history record,
does not reserve a number, and does not upload a permanent artifact.

Final generation calls the concurrency-safe `issue_job_transmittal` RPC. The
RPC validates the job, allocates or confirms a globally unique document
number, and persists one immutable JSON snapshot. Permanent PDF generation is
separate and retryable. It renders only that snapshot, uploads once to the
private `job-transmittal-documents` bucket, and returns a short-lived signed
URL for preview or direct download.

Transmittal numbers use the last four digits of the job number plus a
three-digit suffix. Automatic allocation starts no lower than `002` and checks
both existing job-linked Purchase Order numbers and issued Transmittal
numbers. Manual overrides are normalized and checked against both domains.

Generated Transmittals intentionally do not create `job_attachments` records
and do not appear in Production Project Files. They remain first-class,
immutable Transmittal history records owned by the job.

TenOps currently uses its anonymous Supabase MVP client behind a browser-local
shared-password gate. Transmittal issuance, provisional numbering, and
sanitized job history are exposed only through bounded, validated
business-specific RPCs. The raw Transmittal table, immutable snapshots,
generation claims, storage metadata, document hashes, number registry, and
sequences remain private. Sender names are attributed snapshot values rather
than verified identities.

The service-role Edge Function accepts only exact configured origins and
strict action-specific request shapes. It derives permanent document inputs
and storage identity from persisted state. These controls reduce exposure but
do not authenticate callers. This model is appropriate only for controlled
internal testing and must not be publicly exposed. Supabase Auth and RBAC will
later replace anonymous RPC grants and establish user-level authorization.
Letter of Transmittal is a standard Production capability exposed from the
Production Inspector Documents section.

Purchase Orders and Transmittals share a durable document-number registry.
Their existing domain tables remain separate, but both allocation paths reserve
the same normalized job-prefix namespace transactionally.
