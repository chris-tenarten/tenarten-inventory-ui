## Accepted policy and implemented boundary

Explicitly submitted text may include Job/customer/personal context and message/document excerpts. It may be processed by the configured provider for that user's requested answer. This is distinct from independently retrieving private DMs, tasks or restricted records, which remains prohibited. The ordinary-word private-content case is therefore a positive explicit-input regression under the clarified policy, not a semantic DLP failure. No perfect semantic detection is claimed.

- The server rejects caller-replayed turns and loads only an authenticated owner's private TenBot conversation. A caller provides a conversation ID and optional fixed module label, never authenticated prior turns. Other accounts, including application Admins, cannot load/clear another owner's history. Direct table access is revoked with owner policies as an additional boundary. Authenticated callers cannot forge assistant turns through the append RPC: it is service-only and bound to the verified actor supplied by the Edge handler.
- History is separate from ordinary Messaging/Tasks: at most eight turns are retained per conversation, at most two bounded recent turns enter inference, and conversations expire after eight hours without a new turn. Expired rows are retired lazily on that owner's next history access. Clear assistant chat deletes the owned server conversation and its turns. There is no new general transcript browser or cross-account content-reading authority.
- Explicit pasted input remains intact for processing. Summarizing/rewriting explicitly supplied text does not acquire unrelated Contacts or other module guidance/permissions merely because names appear in the text. Source citations still come from the static permission-filtered registry. No database/repository tool, private-record search or knowledge ingestion is introduced.
- Configured-provider AI draft summaries are validated before being returned, and every feedback draft is revalidated before persistence. The local pilot still keeps feature drafting employee-written. The form starts its shareable request/context fields empty instead of copying private chat; it explains exactly what is shared. Confirmation resets after edits; an edited AI summary becomes Employee-written. Only deliberately confirmed fields are submitted to authorized Product review.
- Feedback rejection returns a generic non-content result instead of raising an argument-bearing PostgreSQL exception. The handler rejects invalid/unconfirmed submissions before calling SQL; the direct RPC also rejects without a row/error. Unexpected errors inside these functions roll back their writes and return generic rejection. The local bridge no longer exposes raw invalid-format model responses. Application diagnostics contain no request/prompt/response logging.
- The service client has an explicit fixed-operation allowlist: the existing usage reserve/finish operations plus a write-only assistant-turn operation. It has no assistant-history read or private DM/task retrieval path. Ordinary Messaging, Tasks, Auth, role/grant bundles, Web Push and Qwen3 selection/free-only budgets remain unchanged.
- Employee controls and composer explain configured-provider processing. Historical source/knowledge privacy wording is corrected to prohibit independent retrieval rather than explicitly submitted text. The separately inspected 96-record knowledge ZIP remains unchanged and unintegrated.
