Generate/review only:

1. Use a local Python environment with `scripts/fixtures/intake-demo-final/requirements-pdf.txt` and run `python scripts/fixtures/intake-demo-final/build-pdfs.py` from repository root. The deterministic builder writes PDFs and preview images, then rewrites the manifest with regenerated expected PDF hashes and byte sizes as designed. Check that regeneration preserves the approved manifest hash; stop for review if it differs. Do not silently adopt changed bytes as approved.
2. `node scripts/prepare-intake-demo-final.mjs` validates those local PDFs and produces reviewable seed/cleanup SQL, `approval.json`, a manifest copy and Storage paths under ignored `output/intake-demo/`. Generated approval metadata is a review artifact, not authorization.
3. `node scripts/intake-demo-storage.mjs` defaults to plan, with zero network requests.
4. After preparation, `node scripts/verify-intake-demo-package.mjs` performs offline deterministic/scope/approval checks. It may regenerate temporary local output through the preparation script; it does not execute SQL or make hosted requests.

The original human review package was `output/intake-demo/FINAL-MANIFEST.md`; it is separately prepared review evidence, not a file generated by the preparation script. PDF assets are under `output/pdf/`, with preview images under `tmp/pdfs/intake-demo/`. Generated outputs remain outside Git. The source JSON, pinned PDF builder and tooling reproduce execution artifacts; retain the applicable approval/execution evidence separately for later maintenance review.

Hosted work requires separate approval of exact manifest/hash and focused disposable validation first. Do not use the older eight-Bid seed script for this final package. Do not execute a mutation just because the generator prepared it.

The Storage runner requires explicit environment configuration for the reviewed backend, public API key, Chris authenticated session and service credential. Never commit credential values or environment files.

Cleanup requires its own authorization: validate all fixtures → generated `02-prepare-cleanup.sql` using the existing Admin prepare-delete RPC → Storage runner `remove` mode for exact-path API removals → generated `03-finish-cleanup.sql` using the existing Admin final-delete RPC → verify zero fixture residue. The prepare-delete RPC changes relationship state and is not a read-only audit. Never directly DELETE storage.objects. The normal cleanup writes durable deletion-audit rows; preserve them. Edited or converted demo records are intentionally protected from automatic cleanup. Shared files and new document relationships also require a stop and separate review; do not detach dependencies or delete Jobs to make a reset succeed. Storage removal and database cleanup are separate guarded operations, not one atomic transaction. Coordinate against concurrent edits; uncertain/partial results require inspection and a reviewed resume.
